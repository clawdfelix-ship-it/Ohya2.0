# 團體服／球衣訂製子系統（Phase 1）設計

## 目標

- 建立一個可獨立上線的 `團體服訂製子系統`，支援 `足球、籃球、排球、背心、Polo` 五個品類。
- 提供接近 `fifakitcreator` 的即時編輯體驗，但第一版採用 `半自由編輯器`，不是完全自由拖放畫布。
- 支援 `模板開始` 與 `空白款開始` 兩種入口，最後進入同一個編輯器。
- 支援 `即時自助下單` 與 `提交報價` 雙軌流程。
- 支援 `全隊名單` 輸入，包括姓名、號碼、尺碼。
- 第一版預覽採用 `2D + 2.5D` 效果圖，不做真 3D 旋轉模型。
- 第一版先以 `獨立系統` 方式上線，之後再整合回現有商城的會員、購物車、訂單與支付。

## 非目標

- 不在第一版實作真 3D 模型、自由旋轉或材質級 PBR 預覽。
- 不做接近設計軟件級的 `多圖層自由拖放 / 群組 / 任意變形`。
- 不在第一版完成與現有商城的深度整合，例如共用購物車、共用帳號登入、正式支付流程。
- 不在第一版完成完整生產管理、工單排程、印刷排版、工廠流程。
- 不在第一版加入 AI 圖案生成或 AI 設計助理。

## 現況與設計前提

- 現有 repo 為 `Node.js + Express + EJS` 的傳統 storefront 架構，已有商品、帳號、訂單、admin 等模組。
- 現有前台頁面以 server-rendered 為主，不適合直接承載高互動、重即時預覽的設計器。
- 因此第一版採用 `先獨立、後整合`：
  - 前台訂製器獨立部署與獨立資料表。
  - 後續再把已驗證的資料模型與流程接回現有商城。
- 商業規則已確認：
  - 產品品類：`足球、籃球、排球、背心、Polo`
  - 商業模式：`直接下單 + 報價` 雙軌
  - 定價方式：`混合制`
  - 素材來源：`官方模板庫 + 客戶上傳`
  - 團體落單：`必須支援全隊名單`

## 核心方案

### 推薦方向

- 第一版採用 `方向 B：半自由編輯器`。
- 原因：
  - 比純商品配置器更接近目標體驗。
  - 比完整自由設計器更易落地，風險明顯較低。
  - 可保留未來升級到更自由編輯器與 3D 預覽的空間。

### 半自由編輯器定義

- 每個模板預先定義 `可編輯區域（zones）` 與 `可用規則`。
- 使用者可在區域內進行：
  - 換色
  - 套圖案
  - 加入 logo
  - 加入隊名、球員名、號碼
  - 選擇部分區域顯示與樣式
- 使用者不能在第一版任意拖到任何位置，也不能自由創建無限制圖層。
- 這可同時滿足：
  - 效果圖穩定
  - 模板資產易管理
  - 價格規則易計算
  - 生產資料較容易落地

## 系統範圍

### 1) 產品入口

- 提供兩種開始方式：
  - `模板開始`
  - `空白款開始`
- 使用者先選：
  - 品類
  - 版型 / 模板
  - 領型 / 袖長 / 款式變體（如適用）

### 2) 即時編輯器

- 支援：
  - 多部位配色
  - 圖案套用
  - 官方 logo / 客戶上傳 logo
  - 隊名、球員名、號碼
  - 前後面切換預覽
  - 2.5D 視覺效果圖
- 預留之後擴展：
  - 更多部位
  - 更細位置控制
  - 更高自由度元素編排

### 3) 商業流程

- `標準單` 可直接建立訂單草稿。
- `複雜單` 或 `大貨單` 自動轉為報價請求。
- 使用者也可主動選擇 `先報價`。

### 4) 最小後台

- 第一版後台只做：
  - 模板管理
  - 價格規則管理
  - 報價單查看與處理

## 資訊架構

### 使用者流程

1. 進入訂製器首頁。
2. 選擇品類。
3. 選擇 `模板開始` 或 `空白款開始`。
4. 進入編輯器，完成顏色、圖案、logo、文字設定。
5. 輸入數量、尺碼與全隊名單。
6. 系統根據模板與規則顯示：
   - 可直接下單，或
   - 需提交報價
7. 使用者提交。
8. 系統建立：
   - 訂單草稿，或
   - 報價請求

### 編輯器面板

- `款式面板`
  - 選品類、模板、空白款、基本變體
- `顏色／圖案面板`
  - 主色、副色、區域配色、圖案
- `文字面板`
  - 隊名、球員名、號碼、字色、字型
- `Logo 面板`
  - 官方素材庫、客戶上傳素材
- `名單面板`
  - 球員姓名、號碼、尺碼

## 模板與效果圖模型

### 模板結構

- 每個模板由以下資產組成：
  - `base image`
  - `front / back preview`
  - `shadow / highlight overlay`
  - `zone masks`
  - `print-safe areas`
  - `logo slots`
  - `text slots`

### Zone 設計

- 每個模板含多個 `template_zones`，例如：
  - 前幅
  - 後幅
  - 左袖
  - 右袖
  - 側邊
  - 領口
  - 袖口
- 每個 zone 定義：
  - 可否改色
  - 可否套圖案
  - 可否放 logo
  - 可否放名字／號碼
  - 邊界尺寸
  - 安全範圍
  - 顯示層級

### 效果圖合成

- 第一版以前端即時合成為主：
  - `base image`
  - `zone color fill`
  - `pattern overlay`
  - `logo image`
  - `text rendering`
  - `shadow / highlight overlay`
- 2.5D 效果來自預製陰影與摺痕層，不依賴 3D 引擎。
- 提交時系統需保存：
  - 設計 JSON
  - 前幅快照
  - 後幅快照

## 資料模型

### 核心實體

- `product_types`
  - 品類，例如足球、籃球、排球、背心、Polo
- `templates`
  - 每個具體版型與款式
- `template_zones`
  - 模板可編輯區域與規則
- `design_assets`
  - 官方圖案、官方 logo、字型、色盤
- `customization_sessions`
  - 使用者當前或已提交的設計 session
- `customization_designs`
  - 與 session 對應的最終設計 JSON 與快照
- `team_rosters`
  - 一張設計的球隊名單資料
- `team_roster_items`
  - 單位球員的姓名、號碼、尺碼
- `quote_requests`
  - 報價請求主表
- `quote_request_assets`
  - 客戶上傳的 logo / 圖檔
- `pricing_rules`
  - 基本價、階梯價、附加費、報價條件

### 關鍵設計原則

- `模板` 與 `客戶設計結果` 分開保存。
- `設計本體` 與 `球員名單` 分開保存。
- `快照圖` 與 `可編輯 JSON` 同時保存。
- `標準單` 與 `報價單` 共享同一套設計資料，不做兩套模型。

## 價格與商業流程

### 混合制定價模型

- 價格由以下層次組成：
  - `基本價`
    - 依品類、模板、版型決定
  - `數量階梯`
    - 例如 10-19、20-49、50+
  - `附加費`
    - 印名
    - 印號
    - 額外 logo 位
    - 特殊尺碼
    - 急單
  - `人工覆蓋價`
    - 報價單可由後台人工改價

### 可直接下單條件

- 使用標準模板。
- 編輯行為沒有超出模板規則。
- 價格可由系統完整計算。
- 訂單數量在自動處理範圍內。

### 需提交報價條件

- 非標準設計要求。
- 特殊位置或超出預設區域。
- 客戶上傳素材需要人手審核。
- 某模板或品類被標記為 `報價優先`。
- 件數過大。
- 使用者主動選擇 `先報價`。

## 後台範圍

### 模板管理

- 新增 / 編輯 / 停用模板。
- 上傳模板預覽圖與效果圖資產。
- 定義 zones、logo slots、文字 slots、安全範圍。

### 價格規則管理

- 維護：
  - 基本價
  - 數量階梯
  - 附加費
  - 自動報價條件

### 報價單查看

- 查看：
  - 效果圖快照
  - 設計 JSON 摘要
  - 名單
  - 上傳素材
  - 備註
- 操作：
  - 改價
  - 設交期
  - 回覆客戶
  - 轉訂單

## 技術建議

### 部署策略

- 第一版建議採用 `獨立前端 app + 現有 Node/Express API` 模式。
- 不建議把高互動編輯器直接塞進現有 EJS 頁面。

### 前端

- 建議用 `React` 建立獨立訂製器前端。
- 使用 `Canvas` 作即時合成。
- 如需較易處理互動元素，可採用 `Konva` 或同級封裝。
- 狀態管理需明確拆分：
  - 模板資料
  - 設計狀態
  - roster 狀態
  - 價格狀態
  - 提交流程狀態

### 後端

- 沿用現有 `Node.js + Express`。
- 新增 `customizer API` 路由群組處理：
  - 模板讀取
  - session 存取
  - 名單提交
  - 報價請求
  - 上傳素材
  - 價格計算

### 資產儲存

- 模板資產、官方素材與客戶上傳圖檔要分開管理。
- 上傳素材需要記錄：
  - 原檔
  - 預覽圖
  - 透明背景檢查結果
  - 解像度資訊

## 錯誤處理

### 前端

- 素材上傳失敗時，要保留目前設計狀態。
- 若某 logo 圖檔不符合規格，要提示具體原因：
  - 太細
  - 比例異常
  - 格式不支援
- 價格未能自動計算時，不應阻止提交；應自動轉做報價流程。

### 後端

- `價格規則缺失` 時回傳可操作狀態，並標示該單需報價。
- `模板資產缺漏` 時禁止模板上架，但不影響其他模板。
- `快照生成失敗` 時應保留設計 JSON，供後台重新產圖。

## 驗收標準

### 功能驗收

- 使用者可建立至少以下類型的設計：
  - 足球球衣
  - 籃球球衣
- 使用者可由模板開始，亦可由空白款開始。
- 使用者可完成：
  - 改色
  - 加隊名
  - 加球員名
  - 加號碼
  - 上傳 logo
  - 輸入全隊名單
- 系統可根據規則輸出：
  - 即時估價，或
  - 報價請求

### 視覺驗收

- 前後幅切換順暢。
- 顏色與圖案套用後效果圖不出界、不穿幫。
- 陰影與高光層可令預覽明顯優於純平面色塊。

### 管理驗收

- 後台可上架至少一個模板族。
- 後台可設定至少一套價格規則。
- 後台可查看報價單與相關效果圖。

## 風險與注意事項

- 最大成本在 `模板資產製作`，不只是寫程式。
- 不同品類的 zone 差異必須從第一天就建模清楚，否則日後難擴展。
- 客戶上傳素材品質參差，需要審核與容錯機制。
- 若一開始把價格規則做得太複雜，標準單流程會變得難維護。
- 2.5D 成敗高度依賴模板資產質素。

## 建議分期

### Phase 1

- 足球、籃球優先
- 模板開始 / 空白款開始
- 2D + 2.5D 預覽
- 顏色、圖案、文字、logo、號碼
- 全隊名單
- 直接下單 + 報價
- 最小後台

### Phase 2

- 補齊排球、背心、Polo
- 更多模板與更細部位控制
- 與現有商城整合

### Phase 3

- 更自由編輯能力
- 3D 預覽
- 更完整生產與訂單後台
